# AI 協作工作流程

這些簡寫讓人先決定方向、AI 負責中間工作，最後再由人確認。它們是對話約定，不是 PowerShell 或 npm 指令。

## `/plan-feature`

適用於新功能、登入流程、資料庫異動、跨頁面調整與正式上線。

1. 釐清目標與使用情境。
2. 探索現有程式與可沿用模式。
3. 列出可修改及不可修改範圍。
4. 定義驗證方式、完成條件、風險與回復方式。
5. 依 `docs/plan-template.md` 建立計畫，等人核准後才實作。

錯字、單純重新命名、明確的小型文案或樣式調整不必強制使用。

## `/security-review`

預設只檢查、不修改：

- 搜尋原始碼、建置產物與 Git 歷史中的密鑰和個資。
- 檢查登入、權限、CSRF、XSS、CSP、檔案上傳、SQL 及錯誤日誌。
- 檢查直接與間接套件通告，分清正式環境與開發工具的風險。
- 依 Critical、High、Medium、Low 回報證據、影響與建議。
- 不在輸出中顯示找到的秘密值。

使用 `/security-review --fix` 時，只修正已有明確解法且能驗證的項目；認證架構、資料刪除或正式環境設定仍需人工核准。

## `/simplify`

目標是減少重複、過度抽象與難以維護的分支，不是重新設計：

- 先記錄既有行為與測試。
- 只處理指定範圍，不改文字口吻、版面、API 或資料格式。
- 小步修改並逐步測試。
- 若簡化需要改變公開行為，先停下來說明取捨。

## `/commit-message`

1. 只讀取 staged diff 與近期提交風格。
2. 摘要「為什麼改」及使用者可感知的結果。
3. 建議一則聚焦的 Conventional Commit 訊息。
4. 除非使用者明確要求，不自行 stage、commit、push 或發布。

## 最終人工檢查

- 功能：操作流程是否符合原始需求。
- 內容：文字是否仍是 Dennis 的口吻。
- 視覺：桌機、平板與手機是否自然。
- 安全：公開與私人邊界是否仍成立。
- 發布：測試全部通過後，由人決定是否上線。
